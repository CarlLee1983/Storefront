# Storefront 實際營運功能缺口評估

評估日期：2026-10-02。程式基準：`ba457e3`。範圍：台灣、單一商家、實體家居商品、TWD；不是多商家平台、跨境商城或 ERP 規格。優先級是本次產品判斷，不是官方平台要求所有商家全部照做。

本次只調查與提出建議，未修改產品程式、建立工單、部署或操作真實交易。依據為程式、資料模型、現有測試內容、README／CONTEXT、GitHub 原始規格與官方資料；沒有跑測試、實際登入或驗證線上環境。測試存在不代表本次已通過。

## 判斷

目前是有完整購買主流程的示範商城，具備良好的交易一致性基礎；要成為能接真實訂單的商店，主要缺口是收款後可持續運作的履約、售後、通知、發票及異常復原。應先補這些，再做促銷與顧客成長功能。

這也符合原始 [issue #1](https://github.com/CarlLee1983/Storefront/issues/1) 的定位：第一個最薄端到端切片，刻意排除通知、付款後取消、手動退款、真實金流與庫存異動歷史。原規格當時排除的圖片、分類與搜尋已在後續實作，不能再當作現況缺口。

## 已有能力，應保留

- 商品、單層分類、搜尋、排序、有貨／特價篩選、精選、圖庫與上下架。
- LINE／Google 登入、瀏覽器購物車、結帳收件資訊、本人訂單查詢。
- 下單價格比對、庫存保留、防超賣、結帳冪等、逾期釋放。
- 付款 webhook 驗簽與事件去重、導回查詢、付款前取消、遲到付款重新保留或退款。
- Cloudflare Access 後台保護、調整庫存、訂單狀態篩選與標記出貨。
- canonical／OG／Twitter metadata、手機版與無障礙相關測試、CI 型別／覆蓋率／E2E gates。

主要程式證據：`apps/app/src/orders/queries.ts:21`、`apps/app/src/catalog/stock.ts:7`、`apps/app/src/payments/queries.ts:123`、`apps/app/src/orders/service.ts:97`、`apps/web/src/layouts/Layout.astro:21`、`.github/workflows/ci.yml`。

## P0：開始接真實訂單前，需要有可執行的流程

P0 指能力必須成立，不代表每一步都必須全自動；少量試營運可以用有紀錄、可核對的人工流程，但不能只靠文案承諾。

| 能力 | 目前證據／缺口 | 最小可營運結果 |
| --- | --- | --- |
| 真實收款與退款 | `apps/gateway` 是模擬服務，顧客可選付款成功／失敗；見 `README.md:54`、`apps/gateway/src/pay-page.ts:22`。 | 至少一種實際付款方式完成商家申請、正式收退款、通知與查詢驗證。不能把接好 sandbox 算正式完成。 |
| 付款對帳與異常復原 | App Cron 只釋放逾期庫存與清圖（`apps/app/src/entrypoint.ts:97`）；無背景付款補查。退款在交易提交後呼叫，事件重送不會重新執行退款（`payments/service.ts:95`）。 | 即使付款 webhook 遺失且顧客關窗，仍能找回已收款交易；退款失敗或結果不明可重試／核對，避免重退。金流金額、訂單、退款及入帳可追溯。 |
| 一般退貨、退款與付款後取消 | 僅支援三種付款異常的自動退款（`payments/refund.ts`）；`payments/service.ts:64` 明說沒有手動退款操作。後台「需要處理」只是提示。 | 能記錄客服受理、退貨商品、收回／驗收、退款金額與結果、是否回補庫存；付款後尚未出貨的取消有受控處理。若只退部分商品，須能表示部分退款，或明定並合法處理首版受理範圍。 |
| 可聯絡顧客與交易通知 | 結帳只收姓名、電話、地址；LINE 登入地址是 `.invalid`（`auth/auth.ts:9`），沒有交易通知整合。 | 取得可用聯絡管道；訂單確認、付款結果、出貨與退款能通知顧客並留下紀錄。自動通知須可判斷送達失敗與重送；低量可先人工聯絡。 |
| 發票／交易憑證 | FAQ 承諾電子發票寄登入 email；編輯文件確認無整合（`docs/copy/83-still-life-review.md:54`）。訂單也無發票資料模型。 | 先依商家稅籍與開票方式確認需求；若採電子發票，完成開立、查詢、交付及退款後作廢／折讓流程；統編、載具、捐贈等依實際適用範圍收集。可由外部開票系統處理，但需對回訂單。 |
| 可實際履約的配送流程 | 只有一次 `paid → shipped` 與選填物流單號；已保存出貨時間且有操作人日誌，但無承運商／送達／配送失敗／補正追蹤號流程（`orders/queries.ts:208`、`orders/schema.ts:7`、`admin/service.ts:217`）。地址只是非空文字（`orders/input.ts:36`）。 | 清楚限定可配送地區，攔阻或人工確認不支援地址；出貨可查、物流號可受控補正、延誤與退回有處理紀錄。家具要確認尺寸、搬運與預約條件；可先人工打單和電話預約。 |
| 真實商品、政策與顧客權益 | README 明示尺寸／材質為展示資料；FAQ 和退換貨頁是示範營運說明。所查頁面未見完整商家資訊、隱私告知、交易條款與個資請求流程。 | 換成經核對的商品資訊、實際商家聯絡與交易政策；能受理退貨、爭議、個資查詢／更正等請求。客服 email 可作入口，不必一開始自建工單系統。 |
| 異常處理與還原準備 | 有結構化 log、部署檢查與 CI；repo 未見完整告警、還原演練與收款故障處理紀錄。 | 確認實際環境的監控、退款／待出貨異常通知、資料復原與處理人。這是待補證據，不等於 Cloudflare 沒有備份，也不是此次已證實線上環境故障。 |

成熟平台的訂單管理涵蓋收款、履約、訂單修正、退貨及退款，可作能力對照，不需照搬所有功能：[Shopify 訂單管理](https://help.shopify.com/en/manual/fulfillment/managing-orders)。通知通常由下單、出貨、退款等業務事件觸發：[Shopify 通知](https://help.shopify.com/en/manual/fulfillment/setup/notifications)。台灣金流與發票官方資料另見[來源研究](commerce-capability-reference-2026-10-02.md)。

### 三個容易被「畫面已有」掩蓋的落差

1. **顯示「需要處理」不代表能處理退款。** `apps/app/src/payments/service.ts:64` 無手動重試；`apps/web/src/payments/webhook.ts:54` 也忽略退款事件。閘道允許重試退款，但 App 的 `payments/queries.ts:199` 僅從 `succeeded` 記錄退款結果；外部重試成功後，原本的 `refund_failed` 不會由現有路徑同步成已退款。這是靜態程式推導的失敗情境，本次未執行重現。
2. **有 email 欄位不代表能寄通知。** LINE 的替代 email 無法收信；需要把登入識別和業務聯絡方式分開考慮。不能為了通知而偷偷用 email 自動合併兩種登入的顧客。
3. **有退換貨說明不代表具備售後能力。** 現有五種訂單狀態無法表示退貨處理、部分退款或換貨履約；需要補充記錄與受控操作，而不只是把顯示文字改成「已退款」。

台灣零售業網路交易規範列有商家資訊、商品資訊、確認機制、配送、運費、解除權及爭議處理等要求；本案應依實際經營型態核對：[數位發展部官方規範](https://law.moda.gov.tw/LawContent.aspx?id=GL000024)。蒐集顧客資料也需檢視目的、利用範圍及權利行使方式的告知：[個資法第 8 條](https://law.pdpc.gov.tw/LawContent.aspx?id=FL010627)。這裡辨識產品流程缺口，不作整站法律合規認證。

另有具體文案待改：`apps/web/src/pages/returns.astro:11` 寫收到退貨後「14 個工作天」退款。對依消保法第 19 條解除的情境，第 19-2 條規定取回或收到退回商品次日起 15 日內返還對價；14 個工作天可能跨越此期限，不能直接沿用到正式營運。來源：[政府法規條文](https://laws.gov.taipei/law/LawSearch/LawExport/FL012059?chapterno=5&type=1)。

## P1：讓商店容易經營，依商品與訂單量提早安排

| 功能 | 現況與理由 | 優先條件 |
| --- | --- | --- |
| 後台訂單搜尋、分頁、匯出、處理備註 | `orders/admin-queries.ts:22` 只取最新 200 筆，可依狀態篩選，但無搜尋／分頁；舊單並非被刪除，仍可依已知 ID 查明細。 | 很早補；客服應可按訂單編號、顧客、日期找回舊單，異常單不應因清單上限被忽略。 |
| 庫存異動紀錄與低庫存提醒 | 現在能安全增減庫存，但只更新 `onHand`，沒有持久化異動原因、操作人與流水（`catalog/stock.ts:48`、`admin/service.ts:203`）。 | 首版可小量人工盤點；多人補貨、盤損或退貨開始後應優先補紀錄。多倉／採購系統另案。 |
| 商品規格與可販售變體 | 單一商品一個價格／庫存，材質尺寸在說明內，無變體（`catalog/schema.ts:5`、`CONTEXT.md`）。 | 若同商品有尺寸、顏色等選項，變體庫存、價格與訂單快照須提前；純單規格商品可維持現狀。真實且足夠的商品說明是 P0，結構化欄位是 P1。 |
| 顧客資料、地址簿、跨裝置購物車 | 有社群登入與訂單列表，沒有自助資料管理／地址簿；購物車只在 localStorage。 | 回購與跨裝置使用頻繁時投入；訪客結帳是轉換策略選擇，不是所有商店必備。 |
| 運費、配送方式與交期規則 | 全館含稅免運，目前無運費明細及規則。 | 若商家真的吸收全部運費可延後；大型家具、偏遠地區或不同交期商品不能只沿用通用免運文案。超商取貨依商品尺寸需求決定。 |
| 營運報表與對帳匯出 | 未見營收、退款、淨銷售、待出貨、庫存周轉等報表。 | 基礎金流對帳屬 P0；視覺儀表板、毛利與進階分析是 P1。不要把「付款成功」直接當結算入帳或最終營收。 |

| 商品 SEO 與內容管理 | 已有 metadata，但未見 Product／Offer 結構化資料、sitemap 或後台內容編輯。 | 依自然搜尋與編輯頻率安排；不必先建大型 CMS。 |

Google 說明 Product／Offer 結構化資料可讓商品有資格呈現價格、庫存及配送／退貨資訊，並非保證排名或曝光：[Google Merchant listing 文件](https://developers.google.com/search/docs/appearance/structured-data/merchant-listing)。

## P2：有銷售基礎後再評估

- 優惠碼、滿額折扣、活動排程；目前原價只是展示欄位，售價才是結帳依據。
- 收藏、補貨通知、評價／問答、相關商品。
- 購物漏斗事件與轉換分析、棄單提醒、顧客分群與行銷訂閱。
- 點數、等級、推薦獎勵、禮物卡。
- 多語系、多幣別、跨境、多商家、多倉與 ERP 串接。

這些是候選能力，不是本次評估建議全部實作的 backlog。金額與庫存相關的促銷也須重新設計訂單金額快照、退款分攤與驗證，不能只在前台扣總價。

## 建議的依賴順序與可觀察驗收

1. **先定真實營運契約**：實際商品、配送區域／費用、金流、開票方式、售後政策、可聯絡顧客的方式。驗收：網站承諾都有可執行的商家流程與負責人。
2. **完成真實金流及復原**：收款／退款、定期或人工對帳、異常佇列和有紀錄的處理操作。驗收：正常付款、失敗重試、關窗且通知遺失、退款結果不明等情境不會讓款項無人追蹤或重複退款。沿用既有冪等與防超賣基礎；新金流的期限、取消、退款語意需重驗 ADR 0001，不能假定只換 URL。
3. **完成履約與售後**：出貨與物流號補正、退貨受理、退款／回補庫存、通知、發票或適用憑證。驗收：一張真實業務測試訂單能從成立追蹤至送達，另有退貨退款情境且帳、款、庫存一致。
4. **改善日常效率，再改善轉換**：先訂單搜尋／分頁、庫存流水，再按實際需求做變體、報表、顧客功能、SEO 與促銷。驗收：清單最新 200 筆之外的訂單能被客服搜尋找到；庫存增減可解釋；新增變體不會共用錯誤庫存。

建議首版限制為單一市場、單一真實付款方式、少量單規格商品、單一配送流程；能用人工流程完成的部分可以先人工執行，但必須可追溯。沒有證據需要更換目前技術棧或重寫整站。
