# 台灣單商家家居實體商品購物站：能力對照基準

查閱日期：2026-10-02。這份文件是供產品盤點使用的外部能力基準，**不是本專案的缺口清單，也不是法律合規結論**。「必要」指若要完成一般線上銷售與售後服務，業務流程應有可運作的處理方式；不代表每項都要自行開發或全自動化。綠界與 Shopify 是具體實作參照，不表示應選用這些供應商。

## 能力對照

| 層級 | 能力與可觀察結果 | 官方依據與範圍 |
| --- | --- | --- |
| 必要 | 顧客能確認商品、價格、數量、收件資訊與訂單總額後下單；商家能找到訂單並區分付款和履約進度，顧客收到訂單確認。 | Shopify 將訂單管理分為付款與履約，包含訂單查找、處理、取消及確認通知。[S1] 這是成熟平台的流程參考。 |
| 必要 | 商家能按實際付款結果決定是否出貨；付款逾時或通知漏收時有查詢與人工處理途徑。 | 若採綠界金流，Server 端 `ReturnURL` 傳付款結果；文件要求驗證檢查碼、避免重複處理，並指出前後端通知先後不固定、缺通知時可查詢訂單，模擬付款不可出貨。[S4] 其他金流應按其契約與文件實作。 |
| 必要 | 對自有現貨，能知道可售量與已承諾訂單的量，避免把已承諾的商品再次出售；缺貨與取消後的數量可核對。 | Shopify 區分 `Available`、`Committed`、`Unavailable` 與 `Incoming`，其中 `Committed` 不可再售。[S3] 多倉、進貨中與安全庫存細分可按營運規模決定。 |
| 必要 | 商家能揀貨、包裝、交寄、記錄出貨與配送資訊；顧客有查詢訂單或聯絡商家的方式。 | Shopify 的訂單管理涵蓋履約。[S1] 綠界物流手冊示範建物流單、印託運單、交寄、配送通知、貨態追蹤與異常處理；該流程只適用於選用綠界物流。[S6] |
| 必要 | 顧客能得知退貨／退款處理方式；商家能記錄申請、收回與檢查商品，執行全額或部分退款並同步訂單狀態。 | Shopify 將退貨、退款、換貨分成不同動作，示範收到並檢查商品後退款。[S2] 是否提供換貨與自行申請入口是營運選擇；退貨政策內容須依實際商品與適用規範另行確認。 |
| 條件式 | 選用綠界信用卡收款時，退款方式須依交易階段處理，並有可查核結果；可以由廠商後台操作，不一定要串退款 API。 | 綠界列出關帳、退刷、取消、放棄等操作，並明言不寫此 API 可由後台處理；分期與部分退款等有特定限制。[S5] 此處不得推廣成所有付款方式通用的退款流程。 |
| 條件式 | 選用綠界物流時，依宅配或超取等實際方案建立物流單、印單、追蹤及處理退件；未採該方案不需相應入口。 | 綠界手冊列出超取、宅配、後台手動、平台／模組及 API 串接等方式。[S6] 宅配與超取是可選通路，並非每站都必備。 |
| 條件式 | 採用綠界 B2C 電子發票服務時，串接或後台流程要涵蓋正確開立資料；結帳時的統編、載具、捐贈選項依實際發票方案提供。 | 綠界即時開立 API 說明開立流程及統編、載具、捐贈等參數組合。[S7] **是否須開立、開立時點與發票種類**涉及營業身分和交易情況，須以適用法規及會計作業確認；這份 API 文件不能證明所有店家都必須使用綠界電子發票。 |
| 成長 | 自助退貨／取消、換貨、批次履約、進階庫存狀態與自動通知，可在單量與客服負荷需要時加上。 | Shopify 將自助退貨列為可啟用能力；庫存文件列有額外狀態。[S2][S3] 基本處理可先由商家操作。 |
| 成長 | 商品頁提供與可見商品一致的 `Product`／`Offer` 結構化資料，包括價格與供貨狀態；有確定政策時才標示運費與退貨資料，並驗證結果。 | Google 指出可購買頁面使用 merchant listing 資料，並可顯示價格、供貨、運送與退貨資訊；結構化資料只代表**可能符合**搜尋呈現資格，不保證顯示。[S8] 這是搜尋曝光功能，不是完成交易的前提。 |

## 台灣規範的有限核對

若商家屬公告所指的零售業等企業經營者，且以網路對消費者訂立定型化契約，數位發展部所列應記載事項包括企業資訊、商品資訊、下單前確認機制、交付地與方式、付款方式、運費計價與負擔、退貨／解除權、個資及消費爭議處理資訊。[S9] 這支持把公開政策、聯絡方式與結帳確認列入上線檢查；具體文案仍須按實際商家與商品檢視。

《消費者保護法》第 19 條的通訊交易解除權有合理例外情事；第 19-2 條對**依第 19 條解除**的情況，規定商家於取回商品或收到退回商品之**次日起 15 日內**返還已支付對價。[S10] 這裡是日，不是「工作天」。若政策把所有依法解除的退款一律寫為「收退貨後 14 個工作天」，假日分布可能使實際期限超過 15 日，應核對並修正文案；一般協商退貨、瑕疵處理等不同情況不能不加區分地套用這條期限。

## 使用這份基準時的界線

- 「有處理方式」可由網站、供應商後台及人工客服共同完成；盤點時應檢查責任人、記錄及顧客可見結果，而非只數頁面或 API。
- 退款、退貨、物流、發票是不同流程。訂單狀態應能與金流和履約紀錄對帳；退款不應只改畫面上的文字。[S1][S2][S4][S5]
- 本文件未查證本專案程式碼，也未主張任何功能目前缺失。法律與稅務適用性除上述兩項有限核對外沒有在此確定；若以其作為上線驗收條件，需按實際商家身分、商品與交易情況確認。
