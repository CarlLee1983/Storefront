# 後台導覽重整：功能分組、響應式框架與列表返回狀態

本文件保留 [#129](https://github.com/CarlLee1983/Storefront/issues/129) 已確認的完整交付規格；Problem Statement 描述設計訪談時的問題，不代表所有問題目前仍未處理。原始決策見[設計紀錄](../plans/admin-navigation-design.md)。

截至 2026-10-04：T1 分組導覽與響應式框架已由 [PR #134](https://github.com/CarlLee1983/Storefront/pull/134) 合併，測試與畫面見[驗收紀錄](../acceptance/130-admin-navigation.md)。[T2 #131](https://github.com/CarlLee1983/Storefront/issues/131) 首頁與商品列表搬移、[T3 #132](https://github.com/CarlLee1983/Storefront/issues/132) 商品返回條件、[T4 #133](https://github.com/CarlLee1983/Storefront/issues/133) 訂單返回條件仍未結案；父規格尚未全部完成。

## Problem Statement

管理員目前面對 12 個平鋪、沒有分組的後台功能入口。功能增加後，商品、庫存、訂單、售後、款項、憑證與設定混在同一列，管理員不容易判斷要去哪裡完成工作。窄螢幕以水平捲動承載入口，無法直接掌握功能全貌。

管理員主要使用桌機／筆電，偶爾使用手機。目前進入後台先看到商品管理；從商品或訂單列表進入深層頁面後，返回連結也不保留原列表的搜尋、篩選與頁碼。這讓日常訂單處理與跨功能查找產生額外操作。

## Solution

將後台共用框架改為桌機固定左側導覽、手機抽屜選單，兩種裝置使用相同的四組分類與完整文字入口。桌機群組與入口預設展開，內容超過可用高度時仍可捲動找到所有功能。

| 群組 | 功能與順序 |
| --- | --- |
| 商品與庫存 | 商品管理、分類管理、庫存流水、低庫存提醒 |
| 訂單與售後 | 訂單管理、取消審核、退貨處理 |
| 款項與憑證 | 付款補查、退款待辦、發票待辦 |
| 設定與通知 | 運費設定、信件投遞 |

後台以訂單管理為第一站。側欄持續標示目前頁面所屬功能；明細與編輯頁提供可返回列表的麵包屑，並保留進入前的列表條件。沿用現有色彩、字型與各功能業務流程，集中改善功能查找、位置辨識及返回操作。

## User Stories

1. 作為管理員，我希望能一眼辨認四個功能群組，以便依工作目的找到入口。
2. 作為管理員，我希望商品管理與分類管理放在同一組，以便找到商品維護相關工作。
3. 作為管理員，我希望庫存流水與低庫存提醒放在商品與庫存群組，以便找到庫存查詢與提醒。
4. 作為管理員，我希望訂單管理、取消審核與退貨處理放在同一組，以便查找訂單及售後工作。
5. 作為管理員，我希望付款補查、退款待辦與發票待辦放在款項與憑證群組，以便辨認款項與憑證處理入口。
6. 作為管理員，我希望運費設定與信件投遞有明確的設定與通知群組，以便不用逐項猜測入口所在位置。
7. 作為管理員，我希望主要導覽中每個功能只有一個所屬群組，以便形成穩定的查找習慣。
8. 作為桌機上的管理員，我希望左側導覽固定呈現群組及完整文字入口，以便在操作內容時仍能辨認可用功能。
9. 作為管理員，我希望導覽內容超過可用高度時仍可捲動，以便取得全部 12 個入口。
10. 作為手機上的管理員，我希望透過清楚的選單按鈕開啟抽屜，以便在有限空間內查看功能。
11. 作為使用不同裝置的管理員，我希望手機與桌機有相同的分類和名稱，以便切換裝置時不必重新學習。
12. 作為手機上的管理員，我希望選取抽屜入口後能到達對應頁面並使用內容，以便完成必要操作。
13. 作為手機上的管理員，我希望在 375px 螢幕上仍能找到全部功能且沒有非預期的頁面水平溢出，以便不必左右拖動整個頁面。
14. 作為管理員，我希望進入後台先看到訂單管理，以便從日常訂單處理開始工作。
15. 作為保留舊後台首頁書籤的管理員，我希望該入口仍能進入後台並到達訂單管理，以便既有書籤仍然有效。
16. 作為管理員，我希望商品管理有清楚且可直接開啟的列表入口，以便首頁調整後仍能維護商品。
17. 作為管理員，我希望商品搜尋、篩選、分頁與列表操作在入口搬移後仍正常，以便既有維護工作不中斷。
18. 作為管理員，我希望商品新增、編輯、儲存及取消仍返回正確的商品流程，以便不會被誤導到訂單管理。
19. 作為管理員，我希望原有商品新增及編輯深層網址保持有效，以便既有連結仍可使用。
20. 作為管理員，我希望進入明細或編輯頁後，導覽仍標示所屬功能，以便知道目前位於哪個工作區域。
21. 作為管理員，我希望看到例如「訂單管理 › 訂單編號」的麵包屑，以便辨認所在位置並返回列表。
22. 作為管理員，我希望從商品列表進入編輯後返回時保留原搜尋、篩選及頁碼，以便繼續處理同一批商品。
23. 作為管理員，我希望從訂單列表進入明細後返回時保留原查找條件及頁碼，以便繼續處理同一批訂單。
24. 作為直接開啟深層頁面的管理員，我希望沒有來源列表條件時仍能返回所屬功能的預設列表，以便不會缺少返回途徑。
25. 作為管理員，我希望既有訂單與退款、發票等相關案件捷徑繼續可用，以便沿用既有處理流程。
26. 作為使用鍵盤的管理員，我希望能操作所有導覽入口並清楚看見焦點，以便不依賴滑鼠也能切換功能。
27. 作為使用鍵盤的管理員，我希望能開啟及關閉手機抽屜，關閉時焦點回到開啟按鈕，以便持續操作。
28. 作為使用鍵盤的管理員，我希望抽屜關閉時其中的連結不會取得焦點，以便不會跳到看不見的控制項。
29. 作為使用觸控的管理員，我希望可見連結與控制項至少有 44 × 44px 的點擊範圍，以便可靠操作。
30. 作為使用輔助科技的管理員，我希望導覽、目前功能、主要內容與選單狀態可被辨識，以便理解及操作後台。
31. 作為管理員，我希望保留跳到主要內容與前往前台入口，以便快速移動到需要的位置。
32. 作為管理員，我希望頁面找不到或沒有存取權時仍呈現清楚且一致的框架，以便理解狀況而不暴露受保護資料。
33. 作為熟悉現有後台的管理員，我希望色彩、字型與各功能流程保持一致，以便只需適應新的導覽結構。

## Implementation Decisions

- 共用後台框架負責群組導覽、桌機側欄、手機抽屜及內容區配置。桌機與手機共用同一份群組、入口名稱、順序及所屬功能定義，避免產生兩套分類。
- 本輪沿用單一「管理員」角色。導覽分組是資訊呈現，不建立新的權限、領域實體或業務狀態。
- 桌機顯示固定左側欄，群組與完整文字入口預設展開；不提供只顯示圖示的側欄模式。手機以選單按鈕開啟抽屜，確保內容過高仍可取得所有入口。
- 目前功能依頁面所屬區域判斷。商品新增與編輯屬於商品管理、分類編輯屬於分類管理、訂單明細屬於訂單管理；其他功能標示對應入口。避免把所有無法辨識的頁面默認標示為商品管理。
- 明細與編輯頁在內容上方提供麵包屑，父層可返回對應列表；目前頁面以可理解的標題或識別資訊呈現。
- 後台根入口 `/admin` 改為前往 `/admin/orders`。商品列表移至 `/admin/products`，商品新增及編輯的既有網址保持不變。舊根入口書籤改為進入訂單管理，這是已確認的行為變更。
- 商品列表搬移必須涵蓋 GET 查找與分頁、商品操作 POST、表單目標、分頁連結、儲存後轉址、取消及返回連結，以及測試和 seed harness 中的商品列表入口。不可只更換導覽連結，也不可讓商品操作錯誤地導向訂單流程。
- 列表到深層頁面的連結須攜帶可重建原列表的既有搜尋、篩選及頁碼。由深層頁面返回列表時恢復這些條件；適用的儲存完成轉址與取消連結也須遵循同一返回規則。這是新增的跨頁行為，並非目前已完整具備的功能。
- 沒有來源條件時，返回所屬功能的預設列表。返回目的地限對應的後台列表，不能接受任意外部目的地；不以新增跨裝置偏好儲存實現本輪需求。
- 保留相關案件的既有跨頁捷徑。主要導覽每個功能只有一個群組，不妨礙訂單頁直接連往退款或發票待辦。
- 保留跳到主要內容、後台 `noindex`、前往前台連結、既有無頁尾設計與存取控制。沿用既有 Access 保護及本機 E2E 驗簽／部署檢查約束，不新增登入或繞過驗證的機制。
- 抽屜須支援鍵盤開關、清楚焦點及關閉後焦點返回開啟按鈕；關閉時其中的控制項不可取得焦點。導覽變更不得遮蔽或阻擋頁面必要操作。
- 沿用現有色彩與字型方案，包括既有拉丁字型與中文系統字體決策；調整導覽及內容區配置，不重做品牌或各功能頁內的表單與流程。
- 預期不新增套件、後端 API 或資料庫結構；不改變訂單、庫存、付款、退款、憑證與通知的業務規則。

## Testing Decisions

- **主要驗收邊界為既有瀏覽器端到端操作。** 延伸目前以正式建置及三個 Worker 啟動的 Playwright harness，使用既有管理員驗證、seed、商品／訂單列表輔助工具與 axe 檢查。沿用使用者已確認的操作驗收，不建立另一套測試應用或專用測試 API。
- 好的測試驗證管理員可觀察的結果：看見群組、找到正確功能、到達正確網址、理解目前位置、恢復列表條件、透過鍵盤完成操作。不要以內部陣列形狀、CSS class 名稱、元件層數或特定抽屜實作作為成功條件。
- 測試覆蓋共用後台框架、12 個功能入口、商品／分類／訂單深層頁面、商品列表路徑搬移與商品／訂單列表返回流程。參考既有後台外殼、商品新增與編輯、商品列表、訂單列表與明細、seed guard 的測試案例。
- 在 1280px 桌機確認四組完整文字導覽及全部 12 個入口，並以受限高度檢查後段入口仍可捲動取得。各深層頁面應標示正確所屬功能。
- 在 375px 手機及實際版型切換點附近確認抽屜開關、全部入口可達、選取功能後可操作頁面，且沒有非預期的頁面水平溢出。不以手機所有功能列必須在 header 同一行為驗收條件。
- 驗證 `/admin` 進入訂單管理、商品列表的新入口、既有商品新增與編輯深層網址，以及商品列表操作 POST、分頁、儲存及取消都沒有誤入訂單流程。
- 商品及訂單的列表返回案例使用足以產生非第一頁的資料及有效查找條件。從實際列表點進深層頁面，再由麵包屑或適用返回操作回去，驗證條件、頁碼及結果內容；不得只檢查查詢字串有被複製。
- 驗證中途操作後仍能返回原列表：商品編輯儲存／取消保留來源條件；從帶篩選及分頁條件的訂單列表進入明細，執行一項既有且會提交表單並重新導向明細的操作，再用麵包屑返回，確認原查找條件、分頁位置及結果內容仍正確。不能只測試進入明細後立即返回的情境。
- 補上直接開啟深層頁面時的預設返回，以及不合法或外部返回目的地不會被採用的案例。沿用同一瀏覽器流程邊界驗證。
- 鍵盤案例驗證跳到主要內容、焦點可見、抽屜開關與焦點返回、關閉的抽屜沒有可取得焦點的連結。檢查可見控制項至少 44 × 44px，對代表性桌機、手機開啟／關閉抽屜、深層頁面及既有錯誤頁執行 axe。
- 保留原有 403／404、noindex、前往前台及各功能流程的回歸。將「導覽必須位於單行 header」等舊版型斷言替換為新行為契約，不降低操作與無障礙要求。
- 先執行受影響的後台與返回流程檢查，再完成專案既有 typecheck、coverage 與 E2E gates。更新驗收紀錄，附上桌機與手機畫面及結果；既有或新發現的失敗須據實記錄，不得當作通過。

## Out of Scope

- 各功能頁內的表單、表格內容或業務操作流程全面重整；必要的共用框架、麵包屑、路徑與返回連結調整屬於本輪。
- 跨功能待辦總覽或新儀表板。
- 功能搜尋、我的最愛、選單待辦數字、只顯示圖示的側欄模式及個人化導覽。
- 新增後台角色、分權、多商家、登入方式或變更 Access 安全邊界。
- 更改訂單、庫存、履約、取消、退貨、退款、發票及通知規則。
- 新品牌視覺、字型替換、前台改版、新套件、後端 API 或資料庫遷移。
- 真實外部服務串接、部署與發布網站。
